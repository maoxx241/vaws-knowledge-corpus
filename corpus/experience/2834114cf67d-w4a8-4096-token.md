# 一次 W4A8 容量审计撤回了 4096 token 的通用安全线

2026-08-24 调查 vLLM-Ascend v0.23 时期的 W4A8 dispatch_ffn_combine 行容量问题时，最初讨论试图用一个 batch token 数给出安全边界。复查 C++ 的 GMM1、GMM2、CombineV2 和 epilogue 后，发现这些数字并不处在同一计量单位中。

当时 CombineV2 先以 currentExpertM 参与容量比较，再在 int4 分支把它乘二，后续累加和输出地址又使用转换后的值；GMM1 的容量累计则显式除二。这个源码差异值得调查，但不能直接成为服务错误的已证实根因。尤其每个 rank 接到的是 expert rows，受 top-k、路由倾斜、TP 是否切分 token 和 padding 影响，平均 batch 数无法代替逐 rank 的实际行数。

整理结论时撤回了“4096 以内必然安全”的说法，也没有把一个特定容量配置推导出的不等式写成通用修复。留下的下一步是固定实际算子选择与输入分布，再用单变量对照确认异常是否随该路径变化。本次只有代码审计和条件纠正，没有新的 NPU A/B；其他模型、容量和版本不能据此推断存在同一缺陷。
