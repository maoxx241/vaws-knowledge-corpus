# QLI 集成性能排查：用同环境回切撤回 prefill 退化归因

2026 年 8 月，比较旧 QLI、全量 QLI v2 和混合路由时，单算子优势没有稳定转成服务收益，部分 TTFT 看起来反而变差。早期把跨日期启动的服务结果放在一起比较，忽略了长输出排队、DP 路由和共享 prefix 命中，因而过早把差异归因给 prefill 路由。

代码调查确实找到了设备侧 `max().item()`，并核对 CPU mirror 与设备张量使用同一请求切片后，改为复用 CPU 最大长度。但这只能减少一处同步，不能解释两个方案共同存在的开销，也不能据此认定它造成了秒级 TTFT 差异。

随后在同环境、同编译产物下执行 A→B→A 回切，使用唯一 token prompt、无共享前缀和 `max_tokens=1`，把纯 decode v2 与长输出排队从首 token 测量中隔离。历史分析文件报告，这一受控实验没有看到原先声称的混合路由 prefill TTFT 退化；此前归因被撤回。

本次整理核验了原始调用代码、测试脚本及会话读取的分析文件，没有重新逐请求计算统计，因此不复述精确收益或宣称稳定性能提升。相关集成见 [PR #15320](https://github.com/vllm-project/vllm-ascend/pull/15320)。旧路由只属于该次实验；留给后续排查的经验是先确认数据是否可比，再用最小回切实验分开算子执行、缓存命中和调度排队的影响。
